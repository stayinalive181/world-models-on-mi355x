World models on MI355X

We brought up the open real-time video models we work with on AMD Instinct MI355X cards on Daytona between 12 and 14 September. This is what ran, how fast it ran against the NVIDIA setups we used before, and every fix it took, with the pull requests that send those fixes back upstream.

Three results

  • MiniMax H3 · FastH3 4-stepFour MI355X render a 14.375-second video-and-audio window at 960×544 in 9.30 s. Our four-H100 profile needed 12.98 to 14.4 s for the same window. Eight MI355X hold real time at the full 1344×768 frame: 11.81 s per window.
  • LingBot-World v2 · 14BOne MI355X runs the 704×384 production frame at 16.3 fps, which clears the model's 16 fps clock. On H100 that frame was served from two cards with context parallelism.
  • JoyAI-Video-EditOne MI355X edits a 1248×720 camera stream at 24 fps with 443 ms from camera frame to edited pixels at the median. An RTX PRO 6000 reached 15.8 fps and 1733 ms at the same size.

MiniMax H3: seconds of content per second of compute

Each bar is one 345-frame window, 14.375 seconds of video with audio, generated end to end: text encoding, four DiT forwards, video and audio decode and the file write. The ratio is content seconds divided by wall-clock seconds, so anything right of the 1.0 line keeps up with playback.

LingBot-World v2: native frames per second by card count

Measured with the camera held forward over 30 chunks. The MI355X rows use an incremental Ulysses KV exchange that swaps only the new frames' keys and values instead of the whole cache window on every attention call. It is bit-exact against the stock path over 757 attention calls, and it is what lets two cards beat one on MI355X links.

ABot-World and Helios also moved to single MI355X cards on 14 September after passing the same release gates. Helios needed no code change beyond turning off a CUDA-only FlashAttention 3 hub kernel. ABot-World needed a scaled-dot-product fallback for its flash-attention calls, listed below.

What it took

Everything we changed or worked around to run these models on ROCm, and where each fix now lives.

WhereWhat happened on ROCmStatus
FastVideo platform detectionThe rocm/pytorch images ship no amdsmi Python package, so FastVideo resolved the CPU platform on an AMD GPU. Installing the PyPI amdsmi wheel instead breaks import torch.Pull request FastVideo #1849
FastVideo sparse attentionBackend selection on ROCm crashed with a TypeError for both video sparse attention backends. With that fixed, FastVideo's Triton sparse kernels run on gfx950, match PyTorch references, and one MI355X renders a 1344×768 window in 62.9 s against 87.8 s dense.Pull request FastVideo #1851
fastvideo-kernel installThe Python and Triton parts of fastvideo_kernel import and run straight from the source tree, which is all the sparse path needs. Building its compiled extension with build.sh --rocm fails in the rocm/pytorch 7.14.1 image: CMake cannot enable the HIP language, because the pip-packaged ROCm SDK carries no hip-lang CMake package.Reported FastVideo #1850
ABot-World attentionflash_attention() asserts a flash-attn build and has no fallback, so the model crashes on machines without one.Pull request ABot-World #14
PyTorch caching allocatorWith expandable_segments:True, the ROCm 7.14.1 image stops allocating after 242 tensors of 84 MiB, or 2036 tensors of 1 MiB, with more than 260 GiB still free. The ROCm 10.1 nightly passes the same test, but we keep the setting off on both stacks.Setting
RCCLMulti-card runs need HSA_NO_SCRATCH_RECLAIM=1. With it, Ulysses sequence parallelism over two to eight cards ran without a hang.Setting
FlashDreams runtimeLingBot's engine loads libcudart through ctypes at start-up, and PyTorch's cuDNN attention has no ROCm kernels, so we route it to the flash backend.Carried patch
FlashDreams context parallelUlysses attention re-sends the whole KV window on every call, which made two MI355X slower than one. The incremental exchange above fixes it.Carried patch
torchao FP8torchao 0.17 limited FP8 to NVIDIA compute capability 8.9 and the MI300 family, which kept LingBot's FP8 path off gfx950.Fixed upstream
TheRock nightly torchvisionThe nightly torchvision wheels carry no gfx950 GPU kernels, so operators such as nms fail on the GPU.Avoided

How we measured

Hardware

Daytona MI355X VF spot sandboxes, 308.9 GB of device memory per card, eight cards on one XGMI hop. NVIDIA reference points ran on H100 SXM, RTX PRO 6000 and B200.

Software

ROCm 7.14.1 and PyTorch 2.12.0 from the rocm/pytorch image. JoyAI used the TheRock nightly, ROCm 10.1 with PyTorch 2.13.

MiniMax H3

FastVideo main from 13 September with the ROCm changes listed above applied as runtime patches, one excluded warmup window, then the median of the measured windows at seed 1000. On 15 September the single-card runs were repeated on FastVideo 37d06a8 with the two pull requests applied.

LingBot and JoyAI

Our streaming worker on the box over loopback: native fps over 30 chunks for LingBot, a 60-second camera stream for JoyAI.

Every figure on this page was measured by us on the systems named, except the B200 rows, which are FastVideo's published numbers.
